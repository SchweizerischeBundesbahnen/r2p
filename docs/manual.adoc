== Overview

R2P is a prototype demonstrating RU - RU - partner communication. To keep things lightweight and portable,
the prototype uses Java and H2 (no need for a dedicated database server).

== Quick Start

=== Test and execute the prototype

Define the environment variable `R2P_AZURE_CLIENT_SECRET`

[source,bash]
----
mvn clean verify
mvn spring-boot:run
----

Visit: http://localhost:8080/

**Interactive API Testing:**

- Swagger UI: http://localhost:8080/swagger-ui/index.html
- OpenAPI Spec: http://localhost:8080/v3/api-docs

**Documentation:** Available in `target/docs/` after building:

- `r2p-manual.html` / `r2p-manual.pdf` - User manual
- `r2p-api.html` / `r2p-api.pdf` - API documentation

Note: in order to access secured endpoints, you need to be a member of the AD-group DG_SEC_DEV_R2P_Admin.

==== Database

By default, the prototype uses a H2 in-memory database, so its content is lost when the application is stopped.
In order to persist the data in a file, configure a corresponding datasource via an environment variable, for example:
----
DATABASE_STORAGE=file:C:/devsbb/h2/r2p
----

In order to automatically clean the database in case of a validation error encountered by Flyway, the following environment variable can be set:
----
FLYWAY_CLEAN_ON_VALIDATION_ERROR=true
----

==== Test Data Generation

It is possible to activate an endpoint for generating test data, which can be used to quickly populate the database
with sample trains (including different branches) for testing purposes.

In order to activate it, define the environment variable `R2P_TEST_DATA_ENABLED=true`.

The endpoint is accessible at `/internal/test-data/generate` and can be invoked e.g. from Swagger UI.

=== Deploy on OpenShift

The Docker image is available at `ghcr-private.docker.bin.sbb.ch/schweizerischebundesbahnen/r2p:latest`.

Check the deployment.yaml file and adjust the values in the ConfigMap and in the Secret.

[source,bash]
----
cd openshift
oc project r2p
oc apply -f deployment.yaml
----

== Development

The https://github.com/googleapis/release-please-action[release-please GitHub Action] is used to create releases.
A release includes a docker image as well as portable application (jpackage app-image) for linux, mac and windows.
These portable applications are directly executable without docker or java installed (e. g. exe on Windows).
Furthermore the api documentation and manual are added as PDF.

All commits must follow the  https://www.conventionalcommits.org/en/v1.0.0/[Conventional Commits specification]. This is checked by a github action
and by Husky pre-commit hooks.

To enable the pre-commit hook, run:
[source,bash]
----
npm install
----

In short every commit message must start with a type, followed by an optional scope and a short description, e.g. `feat(train): add new endpoint to share train with partner`.

Supported types are:

- feat
- fix
- docs
- chore
- refactor
- test
- build
- ci

== Open Issues

Here questions are listed to be clarified with the project team. After clarification, an issue should
be created in the issue tracker and the questions here can be removed.

- The default behavior of Jackson is to ignore all unknown properties. This means that if the RU sends additional properties to the partner, they will be ignored and not stored in the database. This can be misleading. Should we instead validate the schema "hard" fail or at least warn the caller that the data structure is not correct? (options: FAIL_ON_UNKNOWN_PROPERTIES add a DeserializationProblemHandler and log a warning)

== Limitations of current implementation
* Performance of train list endpoint is not optimized (n+1 pattern to get partners, no paging)
* Concurrent modifications/merging/deleting of a train may lead to problems (no optimistic or pessimistic locking implemented yet)
